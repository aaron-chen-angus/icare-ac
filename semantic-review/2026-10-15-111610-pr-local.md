# GO-time misalignment and rep-count asymmetries in the AC//LAB arm-curl engine

AC//LAB is a vanilla-JS static web app that scores a 30-second seated arm-curl test from a webcam using MediaPipe pose landmarks. The controller (`app.js`) runs the camera loop, seeds the analysis with a pre-roll ring buffer, and hands captured frames to a pure offline engine (`analysis.js`) that resamples, filters, detects reps and emits a schema-driven summary that `export.js` serializes to CSV/ZIP/Sheets. The cross-module wiring is largely sound: every `export.js` function the controller imports exists and is exported, the chart specs match what `charts.js` draw() reads, and the CSV writer tolerates missing summary keys. The one runtime-affecting defect is a mismatch between how the controller defines GO-time and how the analysis engine reconstructs it, which shifts the entire scored window.

Watch for:
- **GO-time base disagreement** (confirmed) — the controller seeds frames with a ~2.5 s ring buffer but the engine assumes GO is only `preRollS` (1 s) after the first frame, so the 0–30 s scoring window is offset by ~1.5 s.
- **`t_half_s` sign guard never triggers** (confirmed) — the counted-window test `tHalf >= 0` is applied to a pre-roll-relative time that is legitimately negative, affecting first/second-half bucketing, not counting.
- **`findForward` falls back to the segment start on failure** (likely) — a rep that never crosses 0.5/0.9 still produces finite event times equal to the onset, yielding zero-duration curl phases rather than blanks.

**Verdict**: NEEDS_CHANGES

## High-level view

All twelve `export.js` functions the controller calls (`buildResultZip`, `downloadBlob`, `saveHistory`, `getHistory`, `setFinalLocal`, `clearHistory`, `outboxCount`, `buildPayload`, `uploadSheets`, `queueOutbox`, `flushOutbox`, `buildFinalizePayload`) are present as named exports, so there are no missing-symbol errors on load.

The summary row is assembled in two layers: `buildSummary()` fills participant/device/protocol fields, then `runAnalysis` spreads the analysis-derived summary on top. The CSV writer iterates `SESSION_FIELDS` keys and emits `''` for anything absent, so a partial summary degrades to blank columns rather than a column-count mismatch. The one bookkeeping smell is `attempt_no` being written twice on every path.

The real problem is temporal. The controller treats GO as the last ring-buffer timestamp (correct for the live counter), but the offline engine independently reconstructs GO as `frames[0].t + preRollS*1000`. Because the ring buffer is sized at `ringBufferS` (2.5 s) and `preRollS` is 1 s, the engine's GO lands ~1.5 s before the true GO, and every window-dependent decision — the counted-rep window, first/second-half split, pre-roll posture checks, MOVED_BEFORE_GO — is computed against a shifted zero.

Rep detection is a two-state progress machine with hysteresis. Two edge behaviors matter: the counted-window guard uses a `>= 0` test on a time base that is intentionally negative, and the forward event-search helpers fall back to the segment start rather than signalling "not found," which fabricates zero-length phases for degenerate segments.

### GO-time base disagreement between controller and engine

This is the one defect that changes scored output. Two independent reconstructions of GO-time exist and they disagree.

In the controller, `beginTest()` seeds the frame array from the pre-roll ring buffer and anchors GO to the newest ring sample:

```js
S.frames = [...S.ring];                                  // ring holds up to ringBufferS (2.5 s)
S._goRecMs = S.ring.length ? S.ring[S.ring.length - 1].t : 0;   // GO = last ring sample
```

The live counter uses `tGo = (rec.t - S._goRecMs)/1000`, which is correct: new frames pushed after this moment start at `tGo ≈ 0`.

The offline engine reconstructs GO independently from the first frame and a fixed pre-roll:

```js
const preRollMs = C.protocol.preRollS * 1000;   // 1000 ms
const t0ms = frames[0].t;
const goMs = t0ms + preRollMs;                  // assumes GO is 1 s after the first frame
```

`frames[0]` is the oldest ring sample, which `pushRing` keeps for up to `CONFIG.camera.ringBufferS * 1000 = 2500 ms`. So the true elapsed time between `frames[0].t` and the real GO is up to ~2.5 s, while the engine assumes exactly 1 s. The engine's GO lands ~1.5 s *before* the operator's GO.

The downstream `tUni` axis is `resampleSeries(...).t.map(t => t - preRollMs/1000)` — seconds from the *engine's* GO. Everything keyed off that zero inherits the shift:

```
true timeline:   | ring start ......(2.5s)...... GO=0 ...... test (0..30s) ...... tail |
engine assumes:  | t0=frames[0] ..(1.0s).. GO'=0' ................................ |
                                   ^ GO' is ~1.5 s earlier than real GO
```

Concretely: the counted window is `0 <= tHalf <= windowEnd(30 s)`, pre-roll posture is sampled from `t < 0`, and `MOVED_BEFORE_GO` compares pre-GO flexion — all against GO'. Reps performed in the real first ~1.5 s map to engine-negative time and fall outside the window; the window effectively ends ~1.5 s early. The scored `curls_count` and the `curls_first_half`/`curls_second_half` split drift from what the operator timed.

Fix: thread the controller's GO into the engine instead of re-deriving it. `runAnalysis` already builds `meta`; add `goRecMs: S._goRecMs` and set `const goMs = Number.isFinite(meta.goRecMs) ? meta.goRecMs : frames[0].t + preRollMs;` with `tUni` offset by `(goMs - t0ms)/1000` rather than `preRollMs/1000`. Alternatively seed `S.frames` with exactly `preRollS` of ring instead of the whole buffer, so the two definitions coincide.

### The `t_half_s >= 0` window guard

`detectReps` computes the counted flag as:

```js
const inWindow = tHalf >= 0 && tHalf <= windowEnd;
```

`tHalf` is `t[iHalf]`, i.e. seconds from GO, and the pre-roll frames are intentionally at negative time. A rep whose 50% crossing sits just before GO has `tHalf < 0` and is excluded by the lower bound. On its own that is defensible (don't count reps that peaked before GO), but layered on the GO' shift above, the `>= 0` boundary is measured from the wrong origin, so the lower edge rejects a ~1.5 s band of legitimately in-window reps. Once the GO base is corrected, re-examine whether the intended lower bound is `0` or some small negative tolerance.

### Forward event search fabricates zero-length phases

`findForward` and `findForwardDown` use opposite "not found" conventions:

```js
function findForward(p, from, to, thr) {
  for (let k = Math.max(1, from); k <= to; k++) if (p[k-1] < thr && p[k] >= thr) return k;
  return from;   // <-- falls back to the segment start
}
function findForwardDown(p, from, to, thr) {
  for (let k = Math.max(1, from); k <= to; k++) if (p[k-1] >= thr && p[k] < thr) return k;
  return -1;     // <-- signals not found
}
```

`iTop90 = findForward(progress, a, iTop, highPct)` and `iHalf = findForward(progress, a, iTop, 0.5)`. For a shallow attempt whose progress never reaches 0.9, `iTop90` becomes `a`, so `tTop = t[a] = tOnset`, `curl_time_s = tTop - tOnset = 0`, and `top_dwell` / `tempo_ratio` derive from a zero concentric time. These attempts are usually uncounted (full-ROM gate fails), so the summary means — which filter on `counted` — are mostly protected, but the per-rep CSV rows carry fabricated `0` durations rather than blanks, which misrepresents the attempt. Aligning `findForward` to return `-1` and letting callers blank the field (they already guard `iTop90 >= 0 ? ... : iTop` in several places) would make the degenerate case explicit.

### `attempt_no` double-write

On both the normal and cannot-do paths, `attempt_no` is written twice: `buildSummary` sets `attempt_no = S.attemptNo + 1`, then the caller does `S.attemptNo += 1; summary.attempt_no = S.attemptNo`. The later assignment wins and the two values agree, so output is correct today, but the duplicated bookkeeping across two functions is easy to desync in a future edit — collapse it to a single source. (CSV column width is not at risk: `summaryCSV` iterates `SESSION_FIELDS` keys and `csvCell` renders absent keys as `''`, and `cannotDoTest` pre-fills every key, so every row is full-width regardless.)
